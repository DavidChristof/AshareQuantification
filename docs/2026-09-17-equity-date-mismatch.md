# 「工业富联不是跌了吗，当日收益是哪来的？」—— 日点净值一直按前一天的价格写

**日期**：2026-09-17
**起因**：用户看当日收益为正，而唯一持仓工业富联当天是跌的
**结论**：**每天的「日点」净值都被按前一天(D-1)的收盘价写成**，而 `prev_close_equity`
（当日收益的基线）正是取这个点 ⇒ **次日的「当日收益」凭空多算了前一天的涨跌**。
两个独立 bug 叠加导致，已修。

---

## 1. 症状与真实数字

```
601138  100 股 × (61.50 − 62.33)      =  −83.00     工业富联确实跌了（−1.33%）
000792  400 股 × (24.74505 − 24.75)   =   −1.98     今天卖出，相对昨收基本平价
卖出费用                                =   −7.92
                                  合计   =  −92.90   <- 真实的当日收益
```

而界面显示 **+76.10**（`equity 98,808.54 − prev_close_equity 98,732.44`）。**差 169.00**。

## 2. 那 169 是 09-16 当天的涨幅

`prev_close_equity` 取的是 09-16 那条**日点**净值 98,732.44。把它拆开对账：

```
用 09-16 收盘价：400 × 24.75 + 100 × 62.33 = 16,133.00   <- 同日 15:00 那个点用的就是这个
用 09-15 收盘价：400 × 24.71 + 100 × 60.80 = 15,964.00   <- 而「日点」用的是这个
```

**15,964.00 精确到分吻合后者。** 09-16 那天 601138 从 60.80 涨到 62.33（+153）、
000792 从 24.71 到 24.75（+16），合计 **+169** —— 正是被算进 09-17 的那笔。

再验前一天，同样精确吻合：

| 日期 | 持仓 | 表里的「日点」mv | 用当天收盘算 | 用前一天收盘算 |
|---|---|---|---|---|
| 09-15 | 000792×300, 601138×100 | **13,699** | 13,493 | **13,699** ✓ |
| 09-16 | 000792×400, 601138×100 | **15,964** | 16,133 | **15,964** ✓ |

⇒ **不是偶发，是每天如此。**

## 3. 两个 bug 叠加

### Bug A：写日点时「日期」与「价格」不是同一天

`manual_order`（手工下单后）与 `portfolio_apply`（**09:31 自动调仓**，每天必跑）都写了这么一句：

```python
latest = {s: float(sig["close"].iloc[-1]) for s, sig in SIGNALS.items()}
MANUAL_BROKER.snapshot_equity(today, latest)
#                                ^^^^^ 日历日 D      ^^^^^^ 信号表最后一天 = D-1
```

`today = trade_date()` 是**日历日 D**；而信号表最后一行是 **D-1**（当日行情收盘后才刷新）。
两者不同天，写出来的日点就低一天。

### Bug B：本该纠正它的那条路径**永远进不去**

`_sync_manual_equity()` 的非交易时段分支才是「用最新交易日的收盘价写日点」的正确实现，
但它的守卫是：

```python
if hist and str(hist[-1]["date"]) >= latest:
    return
```

`equity_history()` 把**当日日点排在该日最后**；若当天还没有日点，`hist[-1]` 就是
`'D 15:00'`，而字符串比较 **`'2026-09-16 15:00' > '2026-09-16'` 恒为真**
⇒ 这个分支**永远 return，日点从来没被正确写过**。

于是净值曲线上**唯一存在**的「日点」，就是 Bug A 在盘中写下的那个错值 —— 而它
恰好被 `INSERT OR REPLACE` 占住了键 `D`，再也没有人来纠正。

## 4. 修复

1. **新增纯函数 `paper.daily_point_date(latest_data_date, last_trade_date)`** —— 判定日点
   该不该写、写哪天。条件：日期必须等于价格所属交易日；且**账户状态不能跑到 latest 之后**
   （否则会把 D 的成交算到 D-1 的点上 —— 2026-09-14 那次事故）。
2. **`snapshot_equity(..., price_date=)`**：日期与价格所属交易日不一致时**直接抛错拒写**，
   不再默默写进去。不传 `price_date` 时行为不变（`engine.py` 等老调用点零回归）。
3. **`_sync_manual_equity()` 的非交易时段分支**：改用 `daily_point_date()` 判定，并把
   `price_date=latest` 传下去；`INSERT OR REPLACE` 会**覆盖**当天那条错值 ⇒ 自愈。
4. **`manual_order` / `portfolio_apply` 的那两句**改成调 `_sync_manual_equity()` ——
   盘中它会写「实时价 + 小时键」（日期与价格都是「此刻」，一致），收盘后写日点。

### 我在这轮里自己造的一个 bug（已删）

第一版 `daily_point_date` 我还加了第三个条件 `earlier_point_exists`（想防「服务停摆一周后
重启、用今天的账户状态覆盖很久以前那天的点」）。写完一验：**它几乎恒为真**，
会把**每一次正常的日点写入**都挡掉 —— 修复等于自伤。
实际上条件 2 已经覆盖那个场景（停摆期间账户动过则 `ltd > latest` 直接拦；没动过则
当前状态**就是**那天的状态，重写是幂等的）。
**教训：守卫条件必须拿真实时序走一遍，别凭想象加。**

## 7. 遗留

1. **`_sync_real_equity()` 有完全相同的守卫 bug**（`api/main.py` 里
   `if hist and str(hist[-1]["date"]) >= latest: return`）。**刻意没改**：
   它的价格来自 `_real_prices()`（实时价），改成 `latest` 的收盘价需要另找一个
   按日期的收盘价来源；只修守卫会**开始写入**错值，比现状更糟。目前实盘账户空仓，
   等价于「什么都不写」，没有坏数据。要修得连价格来源一起改。
2. 排查过程中我先后给出过两个**错误**的机制假设（「日期来自 DB、价格来自内存」、
   「信号表最后一行陈旧」），都被探针否掉了：
   - `_latest_data_date()` 读的**也是** SIGNALS，不存在两源不一致；
   - 实测信号表最后一行 `[2026-09-16, 24.75]` 与 `market.db` **逐值一致**。
   ⇒ **不要凭"看起来合理"就下结论；先写能证伪的探针。**

## 8. 教训

1. **「日期」和「价格」是两个字段，但它们必须来自同一天。** 只要代码里出现
   「用 A 的日期 + B 的价格」，就一定会有人写出这种 bug —— 应该在**接口层**拦住
   （本次的 `price_date` 校验），而不是靠每个调用点自觉。
2. **一个永远为真的守卫，比没有守卫更危险。** 它让正确的路径静默失效，
   同时让错误的路径成为唯一的数据来源 —— 而且看起来"有防护"。
   字符串比较 `'D 15:00' > 'D'` 这种坑，值得单独写一条测试。
3. **沉默的错误数据会长期存活。** 全流程零异常、零告警，直到用户肉眼看出来
   「工业富联跌了怎么还赚了」。**账本类的量应该配恒等式护栏**（如
   `当日收益 == Σ 持仓当日盈亏 + 已实现盈亏 − 费用`），跑批后自动核对差额。
4. **我把两个错误假设讲得很肯定，是错的。** 今天第三次了 —— 先探针，再结论。
