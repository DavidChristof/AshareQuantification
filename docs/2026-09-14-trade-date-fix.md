# 事故：成交/记账日期取自「行情数据最后一天」——净值曲线与成交记录日期错位

**日期**：2026-09-14（周一）
**发现**：用户看盘时提出「日期是不是不太对，今天已经14号了」，指向**模拟炒股的账户净值曲线**与**模拟成交记录**两处
**影响**：`paper/manual_account.db`（模拟盘）、`paper/real_account.db`（实盘）的**成交日期**与**净值日点**；已修复并还原数据

---

## 1. 现象

- **模拟成交记录**：最新一笔显示 `2026-09-11`，但今天（09-14）实际发生了 2 笔卖出
- **账户净值曲线**：日点停在 09-11，且 09-11 那天**自相矛盾**

| `paper_equity` 行 | cash | 说明 |
|---|---|---|
| `2026-09-11`（日点） | **75912.94** | 卖出**后** ← 被今天的账户状态覆盖 |
| `2026-09-11 15:00`（盘中点） | **58217.52** | 卖出**前** |
| `2026-09-14 09:00` | 58217.52 | 今天 09:41 服务刚起时 |
| `2026-09-14 10:00` | **75912.94** | 成交后 |

`snapshot_equity()` 读的是账户**当前**现金，而现金只在买卖时变动 ⇒ **cash 从 58217.52 跳到 75912.94 的那一刻就是那 2 笔卖出的时刻**（今天 09:41~10:05 之间）。而它们的日期却被写成了 09-11。

---

## 2. 根因：把「行情数据最后一天」当成了「今天」

行情数据是**收盘后**才刷新的（config `auto_refresh.update_time: 15:30`），所以**盘中/盘前**「信号表最后一天」还停在**上一个交易日**。而项目里到处用：

```python
today = str(sig.index[-1].date())      # ← 这是"数据覆盖到哪天"，不是"今天"
```

周一盘中执行 → `today` = 上周五 → 成交记到上周五，`INSERT OR REPLACE` 还把上周五的净值日点覆盖成今天的账户状态。

**这不是本次改动引入的**，`git blame` 显示来自初始提交 `0346be7`（2026-09-03，DavidChristof）。

### 共 6 处，且**必须一起改**

| # | 位置 | 用途 |
|---|---|---|
| 1 | `portfolio_apply` | 组合调仓的成交日期 + 结尾的净值快照 |
| 2 | `manual_order` | 手动记账的成交日期 + 净值快照 |
| 3 | `_apply_manual_stops` | **止盈/止损卖出**的成交日期（`maxd`） |
| 4 | `_real_positions_payload` | 实盘 T+1 可卖判断 |
| 5 | `real_plan` / `real_check` | 实盘 T+1 可卖判断 |
| 6 | `real_order` | 记账订单的**默认日期** |

> ⚠️ **第 4~6 处是最容易漏的连带坑**：`sellable_shares(symbol, date)` 是
> `持仓 − WHERE date=? AND side='buy'` —— 用**日期字符串精确匹配**当日买入。
> 如果只把「成交日期」改成日历日期、而 T+1 校验还在用数据日期，
> **当天买入会被判成可卖，T+1 静默失效**。所以这两件事必须同源。
> `tests/test_trade_date.py::test_t1_check_must_use_same_date_as_recording`
> 把这个耦合钉死了（同时断言"用错日期会误判"）。

## 3. 修法

`quant/trading/paper.py` 新增单一事实来源：

```python
def trade_date(d: date | None = None) -> str:
    """成交/记账/净值点用的「今天」——**日历日期**，不是行情数据的最后一天。"""
    return (d or date.today()).isoformat()
```

`api/main.py` 原本那个 `_signal_date()`（body 就是取数据日期）更名为 **`_latest_data_date()`**，
把「今天」和「数据日期」两个概念彻底分开：

- **`trade_date()`** = 今天。用于：记账、成交日期、T+1 判断、订单默认日期 → 共 10 处
- **`_latest_data_date()`** = 数据覆盖到哪天。**仅**用于「把净值日点对齐到交易日」
  （`_sync_manual_equity` 非交易时段分支、实盘同理）—— 「收盘点」属于**交易日**，
  是市场概念，不是日历概念。周末不该产生净值点。

`_apply_manual_stops` 里原先只为算 `maxd` 而构造的 `dates` 列表一并去掉。

**没有改动**任何阈值、费用、风控、选股逻辑。

## 4. 已污染数据的还原

数据库先备份到 `paper/manual_account.db.bak_20260914`，修复在**单个事务**内完成：

**① `paper_trades`：2 笔卖出改期**

```sql
UPDATE paper_trades SET date='2026-09-14' WHERE date='2026-09-11';
-- 影响 2 行：id=16 (605117 sell 100)、id=17 (603993 sell 500)
```

**② `paper_equity`：还原 09-11 日点**

原值被今天的账户状态覆盖，按 09-11 收盘重算：

```
09-11 持仓：601600×1000 @9.44 + 000792×300 @25.45 + 601138×100 @64.07
           + 603993×500 @18.15 + 605117×100 @85.50   （后两只今天才卖出）
持仓市值 = 41107.00        现金 = 58217.52（卖出前）
=> equity = 99324.52
```

与 09-11 15:00 的实时点（99317.52）仅差 7 元，是**实时价 vs 收盘价**之差，合理。

> 排查中的一次自我纠正：起初认为这个日点「本不该存在」应删除，
> 但对照发现**每个交易日都有且仅有一个日点行**（含 09-10），说明它是正常结构，
> 只是值被覆盖 ⇒ 改为**还原值**而非删除。

**③ 未改动**：`paper_account.cash` = 75912.94（卖出后，本来正确）、
`2026-09-14 09:00` 点（当时确实还没卖，准确）。

## 6. 遗留 / 未做

1. **同类写法可能还有**：本次只清理了 `api/main.py` 与 `quant/trading/`。其他模块若也把
   数据日期当"今天"，需要同样处理。已用
   `grep -rn "index\[-1\].date()" --include=*.py` 排查，其余命中均为**行情/信号展示**用途，不影响记账。
2. **`manual_order` 的成交价也来自信号表**：`price = float(sig.iloc[-1]["close"])` ——
   数据未刷新时会用**上一交易日收盘价**成交，而不是实时价。这与日期是**两个独立问题**，
   本次未动（改它属于**成交撮合口径**变更，需要单独评估）。
3. **净值曲线 x 轴的混合格式**：`paper_equity.date` 同时存 `2026-09-11` 和 `2026-09-11 09:00`，
   字符串排序会把**当日日点排在当日 09:00 之前**，所以轴上同一天会出现两次、
   且"收盘点"出现在"开盘点"前面。**这是显示层面的既有问题**，与本次日期口径无关，未改。

## 7. 教训

1. **「数据覆盖到哪天」和「今天」是两个概念**，必须用两个函数、两个名字。
   起名时别叫 `_signal_date` 这种含糊的名字 —— 它就是被当成"今天"用了 6 处。
2. **改日期口径前，先找有没有"用日期做等值匹配"的地方**（本例是 T+1）。
   只改写入端不改读取端，会**静默破坏**语义。
3. **`INSERT OR REPLACE` + 错的日期 = 静默覆盖历史**。凡是以日期为主键写历史的，
   调用方给日期前必须自问：这个日期是"事情发生的日子"还是"数据覆盖的日子"？
